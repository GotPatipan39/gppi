# Industrial UI / UX

> เวอร์ชัน 1.2.3 — ดู [CHANGELOG.md](CHANGELOG.md)

ข้อมูลเฉพาะโปรเจกต์ (ชื่อ tag, ช่วงค่าปกติ, ผู้ใช้, ภาษา) อยู่ใน `CLAUDE.md` ของโปรเจกต์ — อ่านก่อนเสมอ ถ้าขัดกับ skill นี้ให้ยึดของโปรเจกต์

## ก่อนออกแบบ ต้องรู้ 4 อย่าง (ถ้าไม่มีใน CLAUDE.md ให้ถาม)
1. **ใครใช้** — operator หน้าเครื่อง / ช่าง maintenance / หัวหน้า / วิศวกร (ใช้ต่างกันมาก)
2. **ใช้ตอนไหน** — เฝ้าดูทั้งกะ / สั่งงานเป็นครั้งคราว / แก้ปัญหาตอนเครื่องเสีย
3. **จออะไร** — touch panel หน้าเครื่อง (อาจใส่ถุงมือ, แสงจ้า) / tablet / จอใหญ่ห้องควบคุม (ดูจากระยะไกล)
4. **อะไรสำคัญที่สุด 3 อย่าง** ที่ต้องเห็นภายใน 2 วินาที

## หลักที่ใช้กับทุกหน้าจอ

### 1. สีมีความหมาย ใช้เท่าที่จำเป็น (แนว ISA-101 high-performance HMI)
- พื้นหลังและสถานะปกติเป็น **โทนเทา/กลาง** — ถ้าทุกอย่างปกติ หน้าจอควรดู "เงียบ"
- **สีสดสงวนไว้สำหรับสิ่งผิดปกติ** ที่ต้องการความสนใจ: แดง = alarm วิกฤต, ส้ม = สูง, เหลือง = ปานกลาง, ฟ้า = แจ้งเตือน/ข้อมูล
- **ห้ามใช้เขียว/แดงบอกแค่ "เดิน/หยุด"** — เครื่องหยุดไม่ได้แปลว่าผิดปกติ ใช้ข้อความ + รูปทรง/ไอคอน + โทนเทาเข้ม/อ่อนแทน
- **ห้ามใช้สีอย่างเดียวสื่อความหมาย** (คนตาบอดสี ~8% ของผู้ชาย, จอ outdoor ซีด) — ต้องมีข้อความหรือรูปทรงประกอบเสมอ
- ใช้ค่าจาก [templates/tokens.css](templates/tokens.css) ไม่ตั้งสีเองในแต่ละหน้า

### 2. ขนาดสำหรับมือ
| จอ | ปุ่มเล็กสุด | ตัวอักษรค่าหลัก |
|---|---|---|
| touch panel หน้าเครื่อง (อาจใส่ถุงมือ) | ≥ 64 px (~15 mm) ระยะห่าง ≥ 12 px | ≥ 28 px |
| tablet / มือถือ | ≥ 48 px | ≥ 24 px |
| จอห้องควบคุม (ดูไกล 2–3 m) | ใช้เมาส์ ≥ 32 px | ≥ 32 px สำหรับค่าที่ต้องเห็นจากไกล |
- ปุ่มอันตราย (stop, reset, delete) ห้ามอยู่ติดกับปุ่มที่กดบ่อย

### 3. ค่าทุกตัวต้องบอกว่า "เชื่อได้ไหม"
- แสดงสถานะการเชื่อมต่อตลอดเวลาที่มุมบน **แยกทีละ link** — browser↔server (WebSocket) และ server↔PLC/ROS ที่ **server รายงานมาเอง** (เช่น อ่าน register ล่าสุดสำเร็จภายในเวลาที่กำหนด) — socket ยังต่ออยู่ไม่ได้แปลว่าได้ข้อมูลจากเครื่อง ห้ามเขียน "PLC เชื่อมต่อ" จากสถานะ socket
- ค่าที่ไม่อัปเดตเกินเวลาที่กำหนด (**stale**) ต้องเปลี่ยนรูปแบบชัดเจน (จาง + ขีด/ไอคอน + เวลาล่าสุด) **ห้ามแสดงค่าเก่าเหมือนค่าปัจจุบัน** — รวม mode, สถานะเครื่อง และสถานะอุปกรณ์ ไม่ใช่แค่ค่าตัวเลข (ข้อมูลหยุดมาได้ทั้งที่ socket ยังต่อ)
- ไม่มีข้อมูล → แสดง `—` ไม่ใช่ `0`
- ทุกค่ามี **หน่วย** และจำนวนทศนิยมที่เหมาะกับความละเอียดจริงของเซนเซอร์

### 4. คำสั่งที่ทำให้เครื่องขยับหรือเปลี่ยนค่า
- **E-stop ต้องเป็นปุ่มจริงทาง hardware** — ปุ่ม stop บนจอเป็นแค่ stop ปกติ ห้ามออกแบบให้เป็นทางหยุดฉุกเฉินทางเดียว และห้ามเขียนป้ายว่า "E-STOP" บนปุ่ม software
- คำสั่งที่มีผลร้ายแรง (start อัตโนมัติ, reset alarm, เปลี่ยน mode, เขียน parameter) ต้องยืนยัน 2 ขั้น และบอกผลที่จะเกิด
- **jog / manual move ใช้แบบ hold-to-run** (กดค้าง = ขยับ, ปล่อย/หลุด connection = หยุด) ห้ามใช้ toggle
- **กดแล้วต้องแสดงผลตามสถานะจริงที่อ่านกลับมา** ไม่ใช่ตามที่กด — ระหว่างรอให้แสดง "กำลังส่ง…" แล้วถ้าไม่ได้รับการยืนยันภายในเวลาที่กำหนด ให้แจ้ง error
- ปิดปุ่มที่ใช้ไม่ได้ในสถานะนั้น (interlock) และ **บอกเหตุผล** ว่าทำไมกดไม่ได้
- **ปุ่ม STOP ห้ามถูกล็อก** ระหว่างรอ ack ของคำสั่งก่อน (รวม STOP เอง) และไม่ขึ้นกับความสดของข้อมูล — ปิดได้เฉพาะตอนไม่มีทางส่งถึง server; STOP ล้มเหลวให้บอกให้ใช้ E-stop ที่ตัวเครื่อง
- **interlock บนจอเป็นแค่ความสะดวก** — PLC/node ต้องตรวจ mode, interlock และช่วงค่าซ้ำทุกคำสั่งเอง (จอ stale, client อื่น, หรือคนเรียก API ตรงข้ามจอได้)

### 5. Local เท่านั้น
- ห้ามโหลด font, CSS, JS, icon จาก CDN/internet — เก็บไฟล์ไว้ในโปรเจกต์ แล้ว serve เอง (เครื่องหน้างานมักไม่มี internet)
- font ภาษาไทย: วางไฟล์ `.woff2` ของ **Noto Sans Thai** หรือ **Sarabun** (OFL ใช้ได้ฟรี) ไว้ในโปรเจกต์ + fallback `Tahoma, "Leelawadee UI", sans-serif`
- ตัวเลขใช้ `font-variant-numeric: tabular-nums` เพื่อไม่ให้ตัวเลขกระโดดตอนค่าเปลี่ยน

### 6. ข้อความบนหน้าจอ
- ใช้ภาษาที่ operator ใช้จริง (ส่วนใหญ่ไทย) — ชื่อ tag/หน่วยเป็นภาษาอังกฤษได้
- **เรียกสิ่งต่างๆ ตามที่ผู้ใช้เข้าใจ ไม่ใช่ตามที่ระบบสร้าง**: "ความเร็วสูงสุด" ไม่ใช่ "D102" หรือ "max_linear_speed" (ชื่อ tag/address ใส่ได้ในหน้าวินิจฉัยระดับ 4)
- **ปุ่มบอกสิ่งที่จะเกิดเมื่อกด**: "บันทึกค่า", "เริ่มเดินอัตโนมัติ" ไม่ใช่ "ตกลง" / "Submit"
- **ใช้คำเดิมตลอดทั้ง flow**: ปุ่ม "บันทึกค่า" → dialog "บันทึกค่า 3 รายการ?" → ผล "บันทึกค่าแล้ว" — operator เรียนรู้หน้าจอจากคำที่ซ้ำกัน
- **ข้อความ error/alarm บอกอะไรเกิด + ต้องทำอะไร** ไม่คลุมเครือ ไม่ขอโทษ: "แรงดันลมต่ำ (4.2 bar) — ตรวจวาล์วลมหลัก" ไม่ใช่ "ERR 0x0042" หรือ "เกิดข้อผิดพลาด ขออภัย"
- **หน้าว่างบอกว่าต้องทำอะไรต่อ**: "ยังไม่มีสูตรการผลิต — กด 'สร้างสูตร' เพื่อเริ่ม" ไม่ใช่หน้าโล่ง
- ข้อความแต่ละชิ้นทำหน้าที่เดียว ตัดคำที่ไม่ช่วยให้ใช้งานง่ายขึ้นออก
- ตัวพิมพ์ใหญ่ทั้งคำ (ALL CAPS) ใช้เฉพาะคำสั่งสั้นที่เป็นมาตรฐานในโรงงาน (START, STOP, AUTO, MANUAL) ไม่ใช้กับ label หรือหัวข้อทั่วไป

### 7. Motion
- ภาพเคลื่อนไหวที่ไม่ได้เกิดจากผู้ใช้ ใช้เฉพาะเพื่อดึงความสนใจไปที่สิ่งผิดปกติ (เช่น alarm ใหม่กระพริบช้า) — ห้ามใส่ animation ตกแต่ง
- การตอบสนองต่อการกด (ปุ่มยุบ, dialog เปิด, แถวที่เพิ่งบันทึกไฮไลต์สั้นๆ) ใช้ได้ เพื่อให้รู้ว่าอะไรเปลี่ยน
- เคารพ `prefers-reduced-motion`

### 8. โครงสร้างทางสายตาคือข้อมูล
- กรอบ, เส้นแบ่ง, ตัวเลขลำดับ, กลุ่ม ต้องบอกความหมาย ไม่ใช่ตกแต่ง — ใส่เลขลำดับเฉพาะเมื่อเป็นขั้นตอนจริง
- ขนาด/น้ำหนักตัวอักษรเรียงตามความสำคัญ: ค่าหลักใหญ่สุด, label เล็กและจาง, ข้อความช่วยเล็กสุด
- ไม่หั่นทุกอย่างเป็นการ์ดหน้าตาเหมือนกันหมด — การ์ดใช้กับสิ่งที่เป็นหน่วยเดียวกันจริง (KPI แต่ละตัว, อุปกรณ์แต่ละตัว)

## ขั้นตอนทำงาน
1. **วางแผนก่อนเขียนโค้ด**: สรุปสั้นๆ — ผู้ใช้/จอ/3 สิ่งสำคัญ (จากหัวข้อด้านบน), โครงหน้าจอเป็น ASCII wireframe, ใช้ token ตัวไหนจาก tokens.css
2. **ตรวจแผนกับโจทย์**: ทุกส่วนต้องมีเหตุผลจากงานนี้ ถ้าส่วนไหนเป็นแค่ค่าเริ่มต้นที่ใส่ทุกงาน (เช่น การ์ดเรียงกันโดยไม่มีลำดับความสำคัญ) ให้แก้ แล้วบอกผู้ใช้ว่าแก้อะไร
3. **เขียนโค้ด** — ระวัง CSS specificity ที่ทับกันเอง (เช่น class ของ section กับของปุ่มตั้ง padding/margin ชนกัน)
4. **ถ่าย screenshot ตรวจเอง** (ถ้าสภาพแวดล้อมทำได้ เช่น Playwright) ทั้งสถานะปกติ / alarm / หลุดการเชื่อมต่อ / จอเล็ก แล้วไล่ checklist ด้านล่าง ก่อนส่งงาน

## ขอบเขต
skill นี้สำหรับหน้าจอที่ใช้ **ทำงาน** (HMI, dashboard, config) — ต้องสม่ำเสมอและคาดเดาได้มากกว่าสวยแปลกใหม่
ถ้างานเป็นหน้าเว็บนำเสนอ/แบรนด์/landing page ที่ต้องการเอกลักษณ์ทางดีไซน์ ให้ใช้ skill `frontend-design` แทน (ถ้าติดตั้งไว้)
