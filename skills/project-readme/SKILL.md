## หลักการเขียน (สำคัญที่สุด)

### 1. ทุกข้อเท็จจริงต้องตรงกับโปรเจกต์จริง
- **อ่านโค้ด/config ก่อนเขียน** — ค่าในตาราง config ต้องคัดจากไฟล์ config จริง พร้อมลิงก์ไปไฟล์นั้น, ชื่อ topic/service/package ต้องตรงกับโค้ด, คำสั่งต้องรันได้จริง
- **ห้ามเขียน feature ที่ยังไม่มี** หรือเดาพฤติกรรม — ถ้าไม่แน่ใจ ให้ถามผู้ใช้ หรือใส่ `TODO(ยืนยัน): ...` แล้วบอกผู้ใช้ในสรุปงาน
- ตัวเลขที่อ้าง (เวลาหยุด, ระยะ, latency) ต้องมาจากการวัดหรือจากผู้ใช้ และบอกว่าวัดอย่างไร ("Measured mid-move: ...")
- ถ้าไม่ได้รันคำสั่งใน README จริง ให้บอกผู้ใช้ว่าคำสั่งไหนยังไม่ได้ทดสอบ

### 2. อธิบาย "ทำไม" กับสิ่งที่ดูแปลก
คนที่มาทำต่อจะ "แก้" สิ่งที่ดูผิด ถ้าไม่มีใครบอกว่าตั้งใจ — README ต้องบอกก่อน
- พฤติกรรมที่ **ดูจากปุ่ม/ชื่อไม่ออก** → อธิบายตรงๆ ("Stop is two presses, not one.")
- สิ่งที่ **ตั้งใจไม่ทำ** → บอกว่าไม่ทำ + ผลถ้าทำ ("`actionStop` is not used. It drops the servos ...")
- ข้อจำกัดที่มาจาก hardware/protocol → อธิบายกลไกจริงหนึ่งครั้ง แล้วโยงว่ามันอธิบายพฤติกรรมไหนบ้าง (หัวข้อแบบ "How X actually works")
- การเลือกที่ **ปฏิเสธแทนการเดา** (refuse ไม่ clamp, ไม่ retry การเขียน, หยุดเมื่ออ่านค่าล้มเหลว) → บอกเหตุผลเป็นตัวอย่างความเสียหายที่ป้องกันได้

### 3. ความปลอดภัยมาก่อน
- ระบบที่ทำให้เครื่องขยับได้: มี `> [!WARNING]` ก่อนส่วนที่สั่งงาน และหัวข้อ "Safety" ที่บอกพฤติกรรมของ Stop / E-stop / การ recover อย่างตรงไปตรงมา
- บอกสิ่งที่ software **ทำไม่ได้** (เช่น ต้องใช้ teach pendant / E-stop จริงในกรณีไหน)
- บอก "ก่อนทำ X ให้อ่านหัวข้อ Y" ตรงจุดที่คนจะเริ่มทำ (เช่น ท้าย Getting started)
- บอกสิ่งที่ไม่มีการป้องกัน (เช่น "rosbridge has no authentication") พร้อมสิ่งที่ต้องทำ

### 4. บอกว่าค่ามาจากไหนจริง
ถ้าค่าเดียวกันตั้งได้หลายที่ (YAML, UI, project file, env var) ต้องบอกลำดับความสำคัญ และค่าไหนต้อง restart / ไม่ต้อง restart

### 5. ติดตั้งได้แม้ไม่มี internet
- ระบุเวอร์ชันที่ต้องใช้ และเหตุผลถ้า pin (เช่น API เปลี่ยนระหว่างเวอร์ชัน, apt มีเวอร์ชันอื่น)
- ถ้ามีไฟล์ติดตั้งเก็บไว้ใน repo (wheel, .deb) ให้บอกคำสั่งติดตั้งแบบ offline
- บอก IP/port ของ deployment ที่ใช้อยู่ และไฟล์ที่ต้องแก้ถ้าเปลี่ยน

### 6. รูปแบบ
- **ภาษา**: ใช้ภาษาเดียวกับ README/เอกสารเดิมของโปรเจกต์; ถ้ายังไม่มี ให้ถามผู้ใช้ (ไทย หรือ อังกฤษ) — ชื่อ topic/package/คำสั่ง คงเป็นภาษาอังกฤษ
- ย่อหน้าแรก 1 ย่อหน้า: ระบบคืออะไร ใช้กับอะไร สร้างด้วยอะไร ทำให้ใครทำอะไรได้
- ตารางสำหรับข้อมูลที่เทียบกันได้ (parameter, interface, step type); prose สำหรับเหตุผล
- bullet แบบ **ตัวหนานำ** — คำอธิบาย ("**Live robot dashboard** — position ...")
- ผังระบบเป็น ASCII ใน code block (แสดงได้ทุกที่ ไม่ต้องพึ่ง renderer)
- ไม่ใช้ emoji ตกแต่ง, ไม่มี badge ที่ต้องโหลดจาก internet, ไม่มีหัวข้อ License/Contributing/Changelog ซ้ำ
- ลิงก์ไปไฟล์ใน repo แบบ relative (`[config](ros2_ws/src/.../config.yaml)`) ใช้ได้ทั้ง GitLab และ GitHub

### 7. Admonition บน GitLab
```markdown
> [!WARNING]
> ข้อความ
```
ใช้ได้ 5 แบบ: `NOTE` (ข้อมูลเสริม), `TIP` (ทางลัด), `IMPORTANT` (ต้องรู้ก่อนใช้), `WARNING` (อันตราย/เสียหายได้), `CAUTION` (ทำแล้วพัง)
- GitHub แสดงเป็นกล่องสี; GitLab รุ่นใหม่ก็แสดงได้ แต่ GitLab ที่ติดตั้งเอง (self-hosted) บางรุ่นจะแสดงเป็น blockquote ธรรมดาที่มี `[!WARNING]` ติดอยู่ — ถามผู้ใช้หรือให้ผู้ใช้เปิดดูบน GitLab ของทีมครั้งแรก
- ถ้า GitLab ของทีมไม่แสดงเป็นกล่อง ใช้แบบนี้แทน (อ่านรู้เรื่องทุกที่): `> **⚠ Warning:** ข้อความ`
- ใช้เท่าที่จำเป็น — ถ้าทุกย่อหน้าเป็น WARNING คนจะเลิกอ่าน

## หัวข้อ — เลือกตามโปรเจกต์
โครงที่ [template.md](template.md) เป็นจุดเริ่ม **ไม่ใช่ทุกหัวข้อที่ต้องมี** เลือกตามที่โปรเจกต์มีจริง:

| หัวข้อ | ใส่เมื่อ |
|---|---|
| ย่อหน้าแรก + `[!IMPORTANT]` สิ่งที่ระบบยังพึ่งอยู่ | เสมอ (IMPORTANT เมื่อมีสิ่งที่คนเข้าใจผิดได้ง่าย) |
| Features | มี UI/ความสามารถหลายอย่างที่ผู้ใช้เลือกใช้ |
| Safety | ระบบสั่งให้เครื่องขยับ/เปิดปิดอุปกรณ์ได้ — **บังคับ** |
| Architecture + ตาราง package/node + "How X actually works" | มีหลาย process/node/อุปกรณ์ |
| Hardware / Wiring / Network | มีอุปกรณ์จริง: รุ่น, การต่อสาย, IP/port/slave ID |
| Prerequisites | เสมอ |
| Getting started / Running in production (PM2/systemd) | เสมอ |
| Configuration (ตาราง + ค่ามาจากไหน) | มีค่าที่ปรับได้ |
| Interface (topic/service/action/API) | มีให้ระบบอื่นเรียกใช้ |
| หัวข้อเฉพาะ domain (sequence, pallet, variable, Modbus ...) | มีแนวคิดที่ผู้ใช้ต้องเข้าใจก่อนใช้ |
| Troubleshooting | มีปัญหาที่เจอซ้ำหน้างาน |
| Project structure | เสมอ (สั้นๆ) |
| Development (+ TIP/CAUTION) | มีคนพัฒนาต่อ |
| Decisions → ลิงก์ docs/adr | มี ADR |

## ขั้นตอนทำงาน
1. อ่าน README เดิม (ถ้ามี), `CLAUDE.md`, `docs/adr/`, config, launch, `package.json`/`package.xml`, `ecosystem.config.js` และโครงสร้างโฟลเดอร์
2. ถามผู้ใช้เฉพาะสิ่งที่หาจากโปรเจกต์ไม่ได้: ภาษา, ใครอ่าน, พฤติกรรมที่วัดจาก hardware, เรื่องความปลอดภัยที่ต้องเตือน (ถ้าต้องถามหลายเรื่องที่ผูกกัน ใช้แนว skill `grilling`)
3. เสนอรายการหัวข้อ (outline) ให้ผู้ใช้ดูก่อนถ้าเป็น README ใหม่ — ถ้าเป็นการแก้ README เดิม แก้เฉพาะส่วน ไม่เขียนใหม่ทั้งไฟล์ และ **คงข้อความเดิมที่ผู้ใช้เขียนไว้** เว้นแต่มันผิด
4. เขียน แล้วตรวจตาม checklist
5. สรุปให้ผู้ใช้: ส่วนไหนตรวจกับโค้ดแล้ว, คำสั่งไหนยังไม่ได้รัน, `TODO(ยืนยัน)` ที่เหลือ

## README ต้องอัปเดตเมื่อ
เปลี่ยนพฤติกรรมที่ README อธิบายไว้, เพิ่ม/ลบ parameter, topic, service, เปลี่ยน IP/port/วิธีติดตั้ง, เพิ่ม ADR — ให้แก้ README ในงานเดียวกัน (commit เดียวกัน) ไม่ทิ้งไว้ทีหลัง และถ้าเห็น README ไม่ตรงกับโค้ดระหว่างทำงานอื่น ให้บอกผู้ใช้
