# Spec และ ticket

> เวอร์ชัน 1.1.0 — ดู [CHANGELOG.md](CHANGELOG.md)

ลำดับงานใหญ่: ซักถามแผน (skill `grilling` + จด ADR ด้วย `domain-modeling`) → **spec** → **ticket** → ทำทีละ ticket (`flowchart` → `tdd` → `git-commit`)
skill นี้ทำ 2 ขั้นกลาง — **ไม่ซักถามเพิ่ม** สรุปจากสิ่งที่คุยกันแล้วและจากโค้ด ถ้าข้อมูลยังไม่พอให้บอกผู้ใช้ว่าควร grill ต่อเรื่องไหน

เก็บเป็นไฟล์ในโปรเจกต์ (อยู่ใน git, คนมาทำต่อเห็น) — ไม่สร้าง issue บน GitLab เอง

## Spec — `docs/specs/<YYYY-MM-DD>-<slug>.md`
1. อ่านโค้ด, `CLAUDE.md`, `GLOSSARY.md`, ADR ใน `docs/adr/` และ flowchart ที่มีอยู่ — ใช้ศัพท์ของโปรเจกต์ เคารพ ADR
2. ร่าง **seam ที่จะ test** (ใช้ seam เดิมก่อน, seam สูงสุดที่ทำได้, ยิ่งน้อยยิ่งดี) แล้วถามผู้ใช้ว่าตรงกับที่คิดไหม
3. เขียนตาม template ข้างล่าง แสดงให้ผู้ใช้ แล้ว**รอ OK** ก่อนแตก ticket
4. commit เมื่อผู้ใช้สั่ง (skill `git-commit`)

```markdown
# <ชื่องาน>
สถานะ: draft | approved (<วันที่>)

## ปัญหา
<จากมุมของผู้ใช้งาน/operator>

## ทางแก้
<จากมุมของผู้ใช้งาน>

## User stories
1. ในฐานะ <operator / ช่างซ่อม / ระบบ WMS / ...> ฉันต้องการ <ความสามารถ> เพื่อ <ประโยชน์>
<ยาวและครบ — รวมกรณีผิดปกติ: สื่อสารขาด, กด STOP, ไฟดับแล้วเปิดใหม่>

## การตัดสินใจ
- <module ที่สร้าง/แก้, interface, protocol, การแบ่ง node/process> — ลิงก์ ADR ถ้ามี

## ความปลอดภัย
- อะไรทำให้เครื่องขยับได้บ้าง และใครสั่ง
- ทางหยุด: STOP, E-stop (ทาง hardware), timeout ของคำสั่ง, เมื่อสื่อสารขาด
- หลัง reset / เปิดเครื่องใหม่ — ไม่เดินเอง
- limit (ความเร็ว, ระยะ, แรง) — ค่าจาก CLAUDE.md หรือ ❓

## ค่า hardware
- ที่รู้แล้ว: ชี้ไปไฟล์+key หรือ CLAUDE.md (ไม่ copy ตัวเลข)
- ❓ ที่ยังไม่รู้: <รายการ — ห้ามเดา ต้องได้ก่อนถึง ticket ที่ใช้>

## Flowchart ที่ต้องมี
- <logic ที่มีลำดับ/เงื่อนไข เช่น sequence ภารกิจ, การรับ-ส่งของ, recovery> → `docs/flowcharts/<ชื่อ>.drawio` (skill `flowchart`)

## การทดสอบ
ระบบตรวจที่ Claude ใช้ตรวจงานเองได้โดยไม่ต้องรอผู้ใช้ไปลองที่เครื่อง: <มีอยู่แล้ว / ต้องสร้าง — simulator, mock_components, Modbus server จำลอง, fake อุปกรณ์, ข้อมูลกล้องที่บันทึกไว้, rosbag> → เป็น ticket 00

| seam | ทดสอบอะไร | ระดับ | ใครรัน |
|---|---|---|---|
| <ฟังก์ชัน/node/topic> | <พฤติกรรม> | unit / simulator / hardware ไม่มีโหลด / ใช้งานจริง | Claude / **ผู้ใช้** (ระดับ hardware ขึ้นไป) |

## ไม่ทำในงานนี้
- <สิ่งที่ตั้งใจไม่ทำ และทำไม>

## หมายเหตุ
```
- ไม่ใส่ path ไฟล์หรือโค้ด (เก่าเร็ว) — ยกเว้นส่วนที่บอกการตัดสินใจได้แม่นกว่าคำพูด (state machine, รูปแบบข้อความ, register map) ใส่สั้นๆ แล้วบอกว่ามาจาก prototype
- user story ของกรณีผิดปกติสำคัญเท่ากรณีปกติ — งานเครื่องจักรพังตรงนั้น

## Ticket — `docs/tickets/<spec-slug>/<NN>-<slug>.md`
1. อ่าน spec ที่ approved แล้ว (หรือบทสนทนา ถ้าผู้ใช้สั่งโดยไม่มี spec) และโค้ด
2. ร่างเป็น **vertical slice**: แต่ละชิ้นผ่านทุกชั้นที่เกี่ยว (เช่น driver → node → topic → HMI) แบบแคบแต่ครบ จบแล้ว**ทดสอบหรือสาธิตได้เอง**, ขนาดพอทำจบใน session เดียว
   - **ticket 00 = ระบบตรวจ** ถ้าโปรเจกต์ยังไม่มี: ของที่ทำให้ Claude ตรวจงานทุก ticket ได้เองโดยไม่ต้องรอผู้ใช้ — Modbus/PLC server จำลอง (skill `modbus` → `tools/modbus_sim.py`), `mock_components`/simulator (skill `ros2-humble-cpp`), fake อุปกรณ์สำหรับ unit test (skill `tdd`), รูป/วิดีโอจากกล้องที่บันทึกไว้ (skill `opencv`), rosbag จากเครื่องจริง — พร้อมคำสั่งเดียวที่รันตรวจทั้งหมด; ticket อื่นทุกตัวรอ 00 — ข้ามได้เมื่อมีครบแล้ว หรือผู้ใช้บอก
     เหตุผล: ไม่มีระบบตรวจ = ทุก ticket ต้องรอคนไปลองที่เครื่อง (คนกลายเป็นตัวส่งต่อผลให้ agent) — ระบบตรวจให้ Claude ทำขั้นที่ปลอดภัยจนจบเอง เหลือแค่ขั้นที่เครื่องขยับจริงที่ต้องเป็นคน
   - งานจัดโค้ดให้แก้ง่าย (prefactor) ทำต่อจาก 00
   - เปลี่ยนชื่อ/ชนิดที่กระทบทั้ง codebase: แยกเป็น เพิ่มของใหม่คู่ของเดิม → ย้ายทีละกลุ่ม → ลบของเดิม แต่ละขั้นเป็น ticket ที่ build ผ่าน
   - **งานที่ทำให้เครื่องขยับ**: ticket แรกของเรื่องนั้นจบที่ simulator/mock; การลองกับเครื่องจริงเป็น ticket แยกที่**ผู้ใช้เป็นคนรัน**
3. แต่ละชิ้นบอก **ต้องรอ ticket ไหน** (ไม่มี = เริ่มได้ทันที)
4. **แสดงรายการให้ผู้ใช้ก่อน**: ชื่อ / ต้องรอ / ส่งมอบอะไร / ทดสอบถึงระดับไหน — ถามว่า ใหญ่-เล็กไปไหม, ลำดับการรอถูกไหม, ควรรวม/แยกตัวไหน — ปรับจนผู้ใช้ OK แล้วค่อยเขียนไฟล์
5. เขียนไฟล์ละ 1 ticket เลขเรียงตามลำดับ (ตัวที่ต้องทำก่อนเลขน้อยกว่า):

```markdown
# <NN>: <ชื่อ ticket>
**สถานะ:** ready | in-progress | done (<commit>)
**ต้องรอ:** <เลข/ชื่อ ticket หรือ "ไม่มี — เริ่มได้ทันที">
**Spec:** [<ชื่อ spec>](../../specs/<ไฟล์ spec>.md)

## ส่งมอบอะไร
<พฤติกรรมที่ใช้ได้จริงเมื่อจบ จากมุมผู้ใช้ ไม่ใช่รายการแก้ทีละชั้น>

## เกณฑ์ว่าเสร็จ
- [ ] <เกณฑ์ที่ตรวจได้>
- [ ] ทดสอบถึงระดับ: <unit / simulator / hardware ไม่มีโหลด — ผู้ใช้รัน>
- [ ] flowchart: <ชื่อไฟล์ ถ้า ticket นี้มี logic ที่มีลำดับ/เงื่อนไข, หรือ "ไม่ต้อง">
- [ ] README/CLAUDE.md อัปเดต ถ้าพฤติกรรมที่คนเห็นเปลี่ยน
```

## ทำงานตาม ticket
- เลือก ticket ที่ตัวที่ต้องรอ done หมดแล้ว — ผู้ใช้เลือกเองได้
- เริ่ม: เปลี่ยนสถานะเป็น `in-progress`; จบ: `done (<commit>)` ใน commit เดียวกับโค้ด
- ระหว่างทำเจอว่า spec ผิดหรือขาด → หยุด บอกผู้ใช้ แก้ spec ก่อน ไม่ทำเลยไปเอง
- ticket ที่เกณฑ์มีระดับ hardware: Claude ทำถึง simulator แล้วส่งให้ผู้ใช้ทดสอบ — ห้ามทำเครื่องหมาย done แทนผู้ใช้
