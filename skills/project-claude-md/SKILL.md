# CLAUDE.md ของโปรเจกต์คุมเครื่อง

> เวอร์ชัน 1.2.0 — ดู [CHANGELOG.md](CHANGELOG.md)

กฎของทีม (rules.md) บอกให้เอาค่า hardware, `ROS_DOMAIN_ID`, เครื่องที่รัน ฯลฯ จาก `CLAUDE.md` ของโปรเจกต์ — ถ้าไม่มี Claude ต้องถามทุกครั้ง หรือแย่กว่านั้นคือเดา
CLAUDE.md ถูกโหลดเข้าทุก session ของโปรเจกต์นั้น: เขียนสั้น ตรง และเป็นสิ่งที่ Claude ต้องรู้ก่อนแตะโค้ด

## เมื่อไหร่
- ผู้ใช้สั่ง (สร้าง/อัปเดต/ตรวจ CLAUDE.md)
- **เปิดโปรเจกต์ที่คุมเครื่อง** (มีโค้ด Modbus/PLC/serial/ROS2 driver/servo/Node-RED ที่สั่งอุปกรณ์) **แต่ไม่มี `CLAUDE.md`** → ถามผู้ใช้ก่อนว่าจะให้สร้างไหม (บอกเหตุผลหนึ่งบรรทัด) — **ไม่สร้างเอง**; ผู้ใช้ไม่เอา → ทำงานต่อโดยถามค่าที่ต้องใช้ตามปกติ
- ผู้ใช้ขอให้ตรวจ CLAUDE.md ที่มีอยู่ → หัวข้อ "ตรวจและอัปเดต CLAUDE.md ที่มีอยู่"
- **จบงานที่ได้ความรู้ใหม่เกี่ยวกับเครื่อง** (ผู้ใช้ยืนยันค่า ❓/⚠️, เจอว่าใครเขียน register ไหน, เจอกับดัก, คำสั่งที่ใช้ได้จริง) → เสนอเพิ่มลง CLAUDE.md แบบ diff สั้นๆ พร้อมเหตุผล แล้วแก้เมื่อผู้ใช้ OK — ไม่จดเรื่องที่แก้ครั้งเดียวจบหรือเห็นได้จากโค้ด

## หลัก: ชี้ไปที่ต้นทาง ไม่ copy ค่า
- ค่าที่อยู่ในไฟล์อยู่แล้ว (`.env.example`, `config/*.yaml`, `params.yaml`, `ecosystem.config.*`, systemd unit) → CLAUDE.md บอกว่า **อยู่ไฟล์ไหน key อะไร** ไม่เขียนตัวเลขซ้ำ — สองที่ที่ต้องแก้คู่กันจะไม่ตรงกันสักวัน แล้ว Claude ไม่รู้ว่าอันไหนจริง
- CLAUDE.md จดเฉพาะสิ่งที่**อ่านจากโค้ดไม่ได้**: ความหมายของ register และค่า, ใครเขียน register ไหน, เครื่องหน้างานต่างจากเครื่อง dev อย่างไร, อะไรทำให้เครื่องขยับ, ข้อห้ามเฉพาะเครื่อง, เหตุผลของสิ่งที่ดูแปลก
- ค่าที่ไม่มีในไฟล์ไหนเลย (เช่น slave ID ที่ตั้งบนตัวอุปกรณ์, comm timeout ที่ตั้งใน drive) → จดใน CLAUDE.md ได้ พร้อมสถานะ

### สถานะของทุกข้อเท็จจริง
| ป้าย | ความหมาย |
|---|---|
| ✅ | ผู้ใช้ยืนยัน หรือยืนยันกับเครื่องจริงแล้ว — ใส่วันที่ (`✅ 2026-10-15`) |
| ⚠️ | อ่านจากโค้ด/เอกสาร/ชื่อตัวแปร ยังไม่ได้ยืนยันกับเครื่อง |
| ❓ | ยังไม่รู้ — **ห้ามเดา** Claude ต้องถามก่อนใช้ |

ป้ายนี้ใช้แบบเดียวกับไฟล์อุปกรณ์ใน skill `modbus` — Claude ที่อ่าน ⚠️ ต้องบอกผู้ใช้เมื่อเอาค่านั้นไปใช้กับเครื่องจริง

## ขั้นตอน
1. **สำรวจแบบอ่านอย่างเดียว** (ไม่รันอะไรที่แตะเครื่อง):
   - โครงสร้าง: `git ls-files`, README, `package.json`/`package.xml`/`CMakeLists.txt`/`pyproject.toml`
   - ค่า: `.env.example`, `config/`, launch/params, `ecosystem.config.*`, systemd unit, docker-compose
   - **`.env` จริงห้ามเปิดอ่านค่า** (อาจมีรหัสผ่าน) — ถ้าไม่มี `.env.example` ให้ดูแค่ชื่อตัวแปร (`grep -oE '^[A-Za-z_][A-Za-z0-9_]*=' .env`) แล้วเสนอให้สร้าง `.env.example`
   - flowchart/เอกสาร (`git ls-files "*.drawio*" "docs/*"`) — แผง REGISTER OWNERSHIP ใน flowchart คือ register map ที่ดีที่สุด
   - MCP: มี `.mcp.json` / `.claude/settings.json` ไหม — ถ้าโปรเจกต์ใช้ระบบที่มี template ใน gppi (`mcp/`: Grafana, PostgreSQL, GitLab, ROS2, Modbus TCP) แต่ยังไม่มี `.mcp.json` → **เสนอ** ให้ใช้ template ในข้อ 3 (ไม่สร้างเอง) — ผู้ใช้มักลืมตั้ง; MCP ที่มีอยู่ต้องอ่านอย่างเดียว และ deny tool ที่เขียนได้ ถ้าไม่ใช่ ให้บอกผู้ใช้
   - ไฟล์คำสั่งของ agent ตัวอื่นที่มีอยู่ (`AGENTS.md`, `SKILL.md` ที่ root, `.cursorrules`, `.agent/`) — **ไม่ copy เนื้อหา** ใช้ `@ชื่อไฟล์` import ใน CLAUDE.md แทน (Claude Code อ่านไฟล์ที่ import ให้เอง)
   - `git log --oneline -30` — รูปแบบ commit, ภาษา, เรื่องที่แก้บ่อย
2. **ร่างตาม [template.md](template.md)** — ทุกข้อมีที่มา (path:key) และป้ายสถานะ; หัวข้อที่โปรเจกต์ไม่มี (เช่น ไม่มี ROS2) ตัดทิ้ง
3. **ถามผู้ใช้ทีเดียวเป็นรายการ** เฉพาะ ❓ ที่สำคัญต่อความปลอดภัยก่อน: อะไรทำให้เครื่องขยับ, อุปกรณ์มี comm timeout ไหม, เครื่องหน้างานคือเครื่องไหน, register ไหนห้ามเขียน — ที่ผู้ใช้ไม่รู้ ให้คงเป็น ❓ ไม่เติมเอง
4. **เขียน `CLAUDE.md` ที่ root** แล้วแสดงให้ผู้ใช้ดู (ไฟล์ใหม่ทั้งไฟล์ หรือ diff ถ้าแก้ของเดิม) — commit เมื่อผู้ใช้สั่ง (skill `git-commit`)
   - มีอยู่แล้ว → แก้เฉพาะส่วน คงข้อความที่ผู้ใช้เขียนไว้ ไม่เขียนใหม่ทั้งไฟล์
5. **ตรวจก่อนส่ง**: `node <skill นี้>/tools/check_claude_md.mjs CLAUDE.md` (error ต้องเป็น 0) + checklist ข้างล่าง

## ตรวจและอัปเดต CLAUDE.md ที่มีอยู่
1. รันตัวตรวจ: `node <skill นี้>/tools/check_claude_md.mjs <path>/CLAUDE.md` — จับ pointer ที่ไฟล์หรือ key หายไปแล้ว (ค่าถูกย้าย/เปลี่ยนชื่อ แต่ CLAUDE.md ยังชี้ที่เดิม), ลิงก์/`@import` เสีย, TODO ค้าง, ค่าที่หน้าตาเหมือนรหัสผ่าน, ไฟล์ยาวเกิน
2. อ่านเทียบกับโปรเจกต์ (อ่านอย่างเดียว): คำสั่งใน CLAUDE.md ยังมีใน `package.json`/launch ไหม, อุปกรณ์/register ที่โค้ดใช้แต่ CLAUDE.md ไม่พูดถึง, ⚠️ ที่ผู้ใช้อาจยืนยันได้แล้ว, เนื้อหาซ้ำกับ rules.md หรือ README, คำแนะนำกว้างๆ ที่ไม่เฉพาะโปรเจกต์
3. **รายงานก่อนแก้** เป็นรายการ: ปัญหาที่เจอ + สิ่งที่ควรเพิ่ม — เรื่องความปลอดภัย (อะไรทำให้เครื่องขยับ, ค่า timeout/address ที่ชี้ผิด) ขึ้นก่อน
4. **เสนอแก้เป็น diff ทีละข้อ** แต่ละข้อมีบรรทัด "ทำไม" (จะช่วย session หน้าอย่างไร) — แก้เมื่อผู้ใช้ OK เท่านั้น, แก้เฉพาะส่วน คงข้อความของผู้ใช้
5. โปรเจกต์หลายส่วน (เช่น `api/`, `ui/`, `scanner/`): ข้อมูลเฉพาะส่วนใส่ CLAUDE.md ในโฟลเดอร์นั้นได้ — Claude Code โหลดเมื่อทำงานกับไฟล์ในโฟลเดอร์นั้น; CLAUDE.md ที่ root เก็บเรื่องทั้งระบบ (เครื่องที่รัน, ความปลอดภัย) และอย่าให้สองไฟล์พูดเรื่องเดียวกัน

แนวคิดการตรวจว่ายังตรงกับโค้ด, รายงานก่อนแก้, diff พร้อมเหตุผล และการเก็บความรู้ท้ายงาน ดัดแปลงจาก anthropics/claude-plugins-official `claude-md-improver` (Apache-2.0)

## สิ่งที่ห้ามอยู่ใน CLAUDE.md
- รหัสผ่าน, token, ค่าจาก `.env` จริง — CLAUDE.md ถูก commit และถูกส่งเข้าแชททุกครั้ง
- กฎที่ซ้ำกับ rules.md ของ gppi (ห้ามเดาค่า, ถามก่อนขยับเครื่อง) — เขียนเฉพาะที่ **ต่างจาก** หรือ **ละเอียดกว่า** กฎทีม เช่น "เครื่องนี้ runtime เป็น Windows + pm2 ไม่ใช่ Ubuntu"
- คำอธิบายสำหรับคน (วิธีติดตั้งยาวๆ, ประวัติ) — อยู่ใน README (skill `project-readme`), CLAUDE.md ลิงก์ไป
- เนื้อหาที่ยาวเกิน ~150 บรรทัด — แยกไปไฟล์ใน `docs/` แล้วลิงก์ หรือ `@import` เฉพาะที่ต้องโหลดทุกครั้ง
